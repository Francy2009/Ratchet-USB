# Testing

## Quick run

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j2
ctest --test-dir build --output-on-failure
```

The unit binary also lists and filters tests:

```sh
build/test/ratchet_tests --list
build/test/ratchet_tests --filter kat
```

Two end-to-end tests are not registered with ctest:

```sh
./test/smoke.sh build/ratchet-usb
python3 test/smoke_ui.py build/ratchet-usb
```

The key schedule has an independent reference implementation:

```sh
python3 test/vectors/reference.py --check
```

## What is covered

- **Unit tests** (`test/test_*.cpp`): KDF, vault, store, X3DH/PQXDH, PQ,
  rollback, Double Ratchet, Triple Ratchet, SPQR bridge, session, message,
  CLI grammar, media, files, secure memory, terminal, screen, UI model.
- **Known-answer tests** (`test/test_kat.cpp`): ChaCha20-Poly1305 (RFC 8439),
  X25519 (RFC 7748), Ed25519 (RFC 8032). These pin the primitives the build
  actually links, not just this project's wrappers.
- **Vectors** (`test/vectors/`): the key schedule is generated by an
  independent Python implementation and diffed in CI.
- **CLI smoke** (`test/smoke.sh`): vault creation, cards, handshake, DH
  ratchet, out-of-order delivery, dash-leading messages, tampering, wrong
  passphrase, rekey, contact removal, and removal followed by a fresh session
  on both sides.
- **Terminal interface** (`test/smoke_ui.py`): a real pty conversation.
- **GUI helper** (`test/test_host_env.cpp`): the AppImage host-environment
  cleanup that makes "Apri cartella" work.
- **Fuzzing** (`test/fuzz/`): parsers, protocol state machine, terminal key
  handling, and the CLI grammar. Committed corpora are replayed on every CI run.
- **Rust**: vendored SPQR and the bridge have their own `cargo test`, plus
  `cargo-audit` and the license inventory check.
- **CI matrix**: gcc/clang, Debug/Release, ASan/UBSan, Valgrind, clang-tidy,
  libsodium's native HKDF and the RFC 5869 fallback, no-GUI build, GUI helper
  tests.

## Coverage

CI builds an instrumented tree, runs the unit tests, the CLI smoke test and
the terminal interface, and publishes `coverage-report` as a workflow artifact.
It is a report, not a gate. To reproduce locally:

```sh
cmake -S . -B build-cov -DCMAKE_BUILD_TYPE=Debug -DRATCHET_BUILD_GUI=OFF \
  -DCMAKE_CXX_FLAGS="--coverage -O0 -g" \
  -DCMAKE_EXE_LINKER_FLAGS="--coverage"
cmake --build build-cov -j2
ctest --test-dir build-cov --output-on-failure
./test/smoke.sh build-cov/ratchet-usb
python3 test/smoke_ui.py build-cov/ratchet-usb
gcovr --root . build-cov --filter 'src/' --exclude 'test/' \
  --exclude 'third_party/' --txt
```

## Fuzzing

```sh
cmake -S . -B build-fuzz -DRATCHET_BUILD_FUZZERS=ON \
  -DRATCHET_BUILD_TESTS=OFF -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=Debug
cmake --build build-fuzz -j2

./build-fuzz/test/fuzz/fuzz_parsers test/fuzz/corpus -runs=0
./build-fuzz/test/fuzz/fuzz_session test/fuzz/corpus_session -runs=0
./build-fuzz/test/fuzz/fuzz_ui_keys test/fuzz/corpus_ui -runs=0
./build-fuzz/test/fuzz/fuzz_cli test/fuzz/corpus_cli -runs=0
```

libFuzzer writes newly discovered inputs into its first directory argument;
point it at `.fuzz-out/`, never at the committed corpora. Growing a corpus is a
deliberate act: add the input that found a bug, not the fuzzer's scratch.

## Not automated yet

- Mutation testing: Mull for C++, `cargo-mutants` for the Rust bridge.
- Differential PQ tests against a second ML-KEM/ML-DSA implementation, and
  OSS-Fuzz.
- The GUI's visual/interaction layer (the host-environment helper is tested).

Manual checks are for platform-specific behaviour that CI cannot reproduce
(for example, a real Fedora file manager) or when production code changes.
Adding tests alone does not require retesting the app by hand.
